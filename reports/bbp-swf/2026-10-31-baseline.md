## Real bugs beyond the keys (candidates; no issues filed)

Each was checked at the case head and again on main at `069eedbcd`. These are
candidates for rusty_mill issues and still need the owner's go.

1. **A session server ignores stdin closing while `wait` blocks, for up to 600 s**
   (932-r1 run 2, P2).
   - Where: `rusty_bbp_host/src/mcp.rs:574-598` (the wait loop) and `serve_on`
     `:803-834`, neither of which polls stdin. The code is unchanged on main.
   - Executed at the head: stdin closed 0.3 s into an 8 s wait, and the server exited
     7.7 s later.
2. **Cancel is refused under a lease when `confine` fails for a never-frozen task**
   (988-r1, all 5 runs, P2).
   - Where: `orch-bbp/src/lib.rs` `cancel` → `freeze` → `lease::confine` (`:862` →
     `:288` on main).
   - Executed with a probe unit test at the head and on main: it returns
     `Permanent("pool member judge is unconfined; …")` and makes 0 BBP calls. The change
     fragment says "Cancel is never refused for a lease".
3. **The lease does not bound the validator profile's `read_roots`, and the docs omit it**
   (988-r1 runs 1 and 4, P2; a design question in runs 2, 3 and 5). Source-traced:
   `rusty_bbp_host/src/runner.rs:323-324`. Candidate code runs with the profile's
   `read_roots`, which `lease.rs` never narrows. ADR-0017, the fragment and
   `RELEASE_NOTES` list every other limitation. **This reaches past the lease, read-only
   and only into roots the operator configured, so it goes to Nano first, not to an
   issue.**
4. **A resumed evidence run is judged only by its last `bbp mod` invocation**
   (763-r2 runs 1, 3 and 5, P1).
   - Source-traced on main: `moderator.rs:1091-1120` allows a capped resume, and
     `marker_text` `:1138` records only the cap and the criteria sha.
     `pairs::facts` reads a single `mod_output` (`pairs.rs:483-557`).
   - An earlier segment's wall stop and build sha are lost, and `spec_wall` treats the
     resume point as a fresh Planning start.
5. **`reads_per_turn` is read from the final card, not the opened budget** (763-r1 run 5,
   P2). Source-traced: `pairs.rs:580` on main reads `st.budget.reads_per_turn` after
   `BudgetExtended` (`rusty_bbp/src/state.rs:908-910`) has applied, so a run opened at 10
   and extended to 30 passes a manifest of 30.
6. **The build-sha "clean" check honours `status.showUntrackedFiles=no`** (763-r2 run 3,
   P2). Executed: `git -c status.showUntrackedFiles=no status --porcelain` hides an
   untracked file. `build.rs:37` and `pairs.rs:707` on main use plain
   `status --porcelain`.
7. **Flaky `tests/review_findings.rs`** (763-r2 runs 2, 4 and 5, P2). Executed: two tests
   share `scratch("completed-ttl-1h")`. In parallel runs, 6 of 20 failed on main; with
   `--test-threads=1`, 0 of 10 failed.
8. **Docs and test gaps on main.**
   - Docs:
     - `bbp mcp` README (`:11`, `:13`, `:140`), `src/lib.rs:4` and
       `src/broker.rs:7-9` still describe one process per turn (932-r1 runs 1 and 4).
     - The host README's `bbp mod` usage omits `--max-usd` and `--criteria`
       (763-r1 runs 1, 2 and 5).
   - Tests (932-r1 runs 2, 3 and 4; 988-r1 run 4):
     - No test covers the launcher refusing a session binding.
     - No test covers the 600 s `timeout_s` cap.
     - The `wait` latency bound (`< 10 s`) never exercises inotify.
     - Nothing tests `relay`'s lease check: deleting it leaves every `orch-bbp` test green.

**Confinement.** No run found a new escape on main. 988-r1 K1 (cross-member symlink swap)
is an escape, and its fix `021d0f01` is on main; the grader confirmed the commit is
there but did not re-test the escape. Item 3 above is the only lease-reach finding open

## Grading

Four grader agents, one per case, graded against the clone at each case head. Each was
told to probe every non-key finding rather than trust the report, and to compare with
main. Findings are the items under a report's "Blocking findings". Design questions and
optional improvements are not graded.

- **Design questions (2).**
  - 763-r1 run 3: the extra N=2 author may use another model. This is stated as intended
    in `changes/2026-10-15-bbp-run-guards.md:7`.
  - 932-r1 run 4: grants-only `wait` rewrites the plan text, which the PR records as
    intended.
- **Re-review rule (763-r2).** No run re-reported an r1 key finding as still open.
  - Runs 1 and 3 tie the resumed-run gap to r1's K1 ("remaining gap in K1"). It is a new
    path that holds at `fa4a8a8a` and on main, so it is graded `real`, not
    `false_positive`.
  - The release-reseal and repeated-flag findings were later-round #763 issues. They hold
    at the head and are fixed on main, so they are graded `fixed_since`.
- **Judgement calls.**
  - 932-r1 run 4 F1 is a K1 catch: the same `shown` mechanism, triggered by a cancelled
    `wait`.
  - 763-r1 run 4 F5 is not a K3 match: it argues the opposite direction.
  - Mixed docs and tests findings are `real` when any part still holds on main.
  - 763-r2 run 1 F6 is graded `real`. It is a "missing tests" finding that groups the
    other findings' tests.
- **Executed versus traced.** Every `real` item above is labelled as executed or

## Notes

- **Capture gap.** Eval-Kit keeps a run's last result message as its report. A run that
  finishes its review and then answers a background-job notification loses the review
  (932-r1 run 5: 5 s, 88k tokens in its header, which is the last turn only). Its
  tokens, time and cost are therefore understated in the 932-r1 row. Worth fixing in
  Eval-Kit (keep the longest or the last report-shaped message) or in the prompt (no
  background jobs).
- First-pass judge rates (29/60) match graded hit rates on every key except 763-r2 K4.
  There the judge passed 2 of 5 runs, while grading found one catch (run 4 F3); the
  other pass (run 1) mentions an unreadable log only in passing, as raising `stop: cap`,
  which is the opposite of the key.
