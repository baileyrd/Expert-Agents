## Real bugs beyond the keys

Confirmed by graders at each case head (probe crates and worktrees under `~/bench-work/grade/`,
outside this repo) and re-checked on rusty_mill `origin/main` at `808d6ebd9`. All of the
following are **still on main**. None filed (per instructions).

- **Fallback runtime leaves a dropped `Child` as a zombie** (P1; 1226-r1, all five runs).
  With `install_fallback()` and no running rusty_tokio `Runtime`, `Child::drop` uses
  `Handle::try_current()` (`process/mod.rs:426` at head, `:431` on main), finds none, and never
  reaps; a `kill_on_drop` child stays `Z`. Executed at head and on main; the control on a
  rusty_tokio `Runtime` is reaped.
- **`Notified::enable` then drop re-banks the permit** (P1–P2; 1250-r1 runs 1, 3, 4, 5).
  `notify_one`, `enable()` → true, drop, then a fresh `notified()` is Ready in rusty_tokio and
  Pending in tokio 1.53.3, contradicting the module doc's "as tokio does" (`notify.rs:31-33`).
  Executed at head and on main.
- **A forwarded `notify_last` goes FIFO** (P2; 1250-r1 runs 1, 3, 4, 5). Waiters A, B, C;
  `notify_last` fires C, C is dropped: rusty_tokio wakes A, tokio wakes B. Executed at head and
  on main (main forwards through `notify_one`, `notify.rs:300-304`).
- **`wait_for` predicate calling `receiver_count()` / cloning a `Receiver` deadlocks** (P1;
  1085-r1 run 1). Both lock the std Mutex the predicate already holds (`watch.rs:110`, `:191`);
  tokio reads a counter without the lock. Executed: hangs at head and on main.
- **Semaphore `add_permits` overflow panics under `state`, and the "no code that can panic
  runs while `state` is held" comment is still false** (P2; 1066-r2 runs 1, 3). Executed:
  `add_permits(usize::MAX)` panics at `semaphore.rs:419` (head) / `:450` (main) with the lock held.
- **No test guards `close()` storing `WAITER_CLOSED` under the lock** (P2; 1066-r1 run 3,
  1066-r2 runs 1, 3). Executed as a mutation: moving the stores after `drop(guard)` passes every
  `lock_cancel` test; traced to a hang on the re-poll path.
- **No test covers barging between release and the woken waiter's re-poll** (P2; 1066-r1 run 1).
  Traced.
- **Change fragment's failing-test count is wrong** (P2; 1066-r2, all five runs): says 8 of
  the new tests fail on base; 9 of 11 do at the head, and main's fragment (8 of 13) is off too
  (10 fail). Executed.
- **Fallback test coverage gaps** (P2; 1226-r1 runs 1–4): no fallback test for process,
  `task::Builder::spawn`, signals, UDP/Unix/pipe/`AsyncFd`. Traced.
- **`notify_last` forwarding and cross-thread drop untested** (P2; 1250-r1 run 4). Traced.
- **Stale docs:** `cancellation_token.rs:7-13` still says a dropped `Notified` stays queued
  (1250-r1 run 4); `rusty_term/l13/Cargo.toml:17` still calls rusty_lsp's `runtime` feature
  "tokio-backed" (1085-r1 runs 1, 2, 3, 5; 1085-r2 run 1). Traced.

Fixed on main since the head (`fixed_since`, 16): the Notify/`CancelToken` waker leak (fixed
by #1250's `Drop for Notified`; 1085-r1 runs 2–5, executed), `changed()` keeping its first
waker (1085-r1 run 5, 1085-r2 runs 1, 3, 5; executed), the false "no code that can panic"
comments in 1066-r1 (fixed by 3280c75e and 6a200213), the stale stdio one-op doc (1085-r2
run 2), `wait_for` happy-path-only tests (1085-r1 runs 2, 3), and the 1250 window test.

## Grading

Graded blind against the clone at each case head by six grader agents, one per case, each
told to verify every non-key finding by execution or source trace rather than trust the
report, and to check `origin/main` for `fixed_since`. Findings are items under a report's
"Blocking findings"; design questions and optional notes are not graded.

- **False positives (3):** 1226-r1 runs 1, 3, 5 flagged the `ASYNC-RUNTIME-INVENTORY.md` note
  as violating an "owner go-ahead per consumer" rule. That rule comes from the expert's own
  grounding, not the repo; the note makes the next steps conditional and approves no consumer.
  `design_question` would also be defensible.
- **Design question (1):** 1085-r1 run 5 F5, a `wait_for` predicate that calls `tx.send`
  deadlocks; tokio's `wait_for` also holds the channel's lock during the predicate, so this is
  shared behaviour. (Run 1's `receiver_count` variant is graded real: tokio completes it.)
- **Judgement calls:** test-gap findings under "Blocking findings" graded (real when still
  true on main); findings bundling a key with other claims matched to the key; 1085-r2 run 5
  labelled its findings "K4"/"K5" and was renumbered F1/F2.

## Run notes

- **Sandbox and network.** Bash ran in Claude Code's sandbox with `$EXPERT_AGENTS`, `$TARGET`
  and `~/.claude` denied to Bash and Read, and network open only to `index.crates.io` and
  `static.crates.io`. No run could reach github.com, so the runs are blind. Smoke test before
  the bench, using the suite's settings: a sandboxed `cat $TARGET/Cargo.toml; ls $EXPERT_AGENTS`
  returned "No such file or directory" and an empty listing, while both exist outside the
  sandbox.
- **Restart.** The first 10 runs (1066-r1, 1066-r2) ran one at a time with Claude's temp
  directory on the 16 GB `/tmp` RAM disk, which their cargo builds filled to 80%. The bench was
  stopped and resumed with `--jobs 4`, `TMPDIR=~/bench-work/tmp` and
  `CLAUDE_CODE_TMPDIR=~/bench-work/claude-tmp` on disk. Settings and run keys were unchanged, so
  stored runs were kept. In the resumed runs four reviewers shared one Claude temp directory,
  so a run could in principle see another's scratch files; each still had its own checkout.
- **Timeouts.** 1085-r1 run 1 and 1250-r1 run 2 hit the 3600 s limit and were re-run once
  (`evalkit run` fills only what is missing); both completed.
- **Shared checkout.** Another thread switched this checkout to its own branch for about a
  minute (19:57:41–19:58:46Z) mid-bench. Eval-Kit had already loaded the prompt, cases and
  settings into memory, and reviewers cannot read the checkout; all 30 stored run keys equal the
  job keys recomputed from the suite at `69ff745`, so no run was invalidated or re-run.
- **Leak note.** The prompt's failure classes "re-entrant waker or value" and "cancelled
  waiter" (`prompt.md:97-100`) overlap 1066-r1 K1 and 1085 K4 (dropped `changed()` wait). They
  come from non-held-out fixes (mpsc, `DuplexStream`, `RwLock`), not from the bench PRs, but
  those two keys' hit rates (1.00) are the most likely to be flattered; read per-case recall.
