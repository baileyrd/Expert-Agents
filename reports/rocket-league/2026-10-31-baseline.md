## Real bugs beyond the keys

Confirmed by graders at each case head (worktrees and probe crates under `~/bench-tmp/`,
outside this repo) and re-checked on rusty_mill `origin/main` at `808d6ebd9`. **All of the
following are still on main.** None has been filed.

**rb_rl_game_bridge (666-r1):**

- **A game that dials first is evicted by later silent connections** (P0–P1; runs 1–5).
  `link.rs:203-207` at head removes `candidates[0]` once eight more connections are waiting,
  and `:233-235` keeps the timeout off while anything waits, so the bridge then waits forever.
  Executed by the reviewers; traced by the grader. On main the behaviour is unchanged
  (`link.rs:237-243`), but `README.md:89-91` (from `2cc049473`) now documents it as a known
  limitation. It is real at the head, whose docs claimed the opposite; on main it is arguably a
  design question.
- **One accept or `setsockopt` error aborts the whole wait** (P2; run 4). `link.rs:201-202`
  (`?`) and `:214` (`return Err(e)`) at head; `:309-310` and `:319` on main. On Windows, `accept`
  can return `WSAECONNRESET` for a peer that resets before it is accepted (traced against
  Microsoft's docs, not executed; run 2's Linux probe of the same case was harmless). Also
  present at the base.

**rb_physics_bullet / tape-bot calibration (1048-r1):**

- **The rest_40 residual is blamed on the wrong cause** (P2; all five runs). The probe sets spin
  for a 91.25 radius (`gen_probes.py:162,176`), but the port's `BALL_RADIUS` is 93.15
  (`body.rs:112`). On tick 1 the port's ball speeds up from 40.000 to 40.231 uu/s while spin
  drops, and it freezes at frame 273 against the game's 242. Pure decay would put it under 40
  after one tick. Executed by the grader. Main: RB-PHYSICS-001:2213-2215 and
  `golden_captures.rs:178`.
- **Quoted residuals do not match the golden harness** (P2; runs 1, 2, 4, 5). Measured at head:
  rest_20 ball max 1.441 (the PR says 1.6), fast_6500 mean 5.680 (5.4), fast_6500 max 56.84 (55).
  The golden bounds are the measured values × 1.25 (`golden_captures.rs:192, 220`), so text and
  bounds disagree. Executed. Main: `changes/2026-10-25-rl-ball-sleep-calibration.md:8`,
  RB-PHYSICS-001:2212 and :4009.
- **The port freezes the ball one tick before the game** (P2; runs 1, 2). In rest_10 the game
  moves on frame 241 and is zero on 242. The port does not move on step 241 because of the `>=`
  check and zeroing before integration in the same call. Executed. Main: `body.rs:477`,
  `world.rs:1527-1532`.
- **The port sleeps a parked car that the game never sleeps** (P2; run 1). The game's parked car
  stays at ≤ 1.88 uu/s and ≤ 0.11 rad/s for about 5 s with no exact-zero frame. The port zeroes
  it from frame 241. The PR says "no car capture measures it", but every rest probe records a
  parked car. Executed. Main: `body.rs:104`, `world.rs:1528-1529`. A grader could call this a
  design question, since the PR says the car thresholds are assumed.
- **Stale doc comments on cap order** (P2; run 2). `world.rs:1213` and `:273-274` say the cap
  runs before transform integration, but `clamp_ball_velocity` runs after
  `integrate_transform_and_refresh_inertia` (`world.rs:1532-1537`). Same on main.
- **Parity doc row is stale** (P2; run 4). `PHYSICS-PARITY-VS-ROCKETSIM.md:91` still calls the
  6000 uu/s cap untested while line 78 says it is settled. Same on main.

Fixed on main since the head (`fixed_since`, 4): the 973 change fragment saying the rolling

## Grading

Graded blind against the clone at each case head by four grader agents, one per case. Each was
told to verify every non-key finding by execution or source trace rather than trust the report,
and to check `origin/main` for `fixed_since`. Findings are items under a report's "Blocking
findings"; optional notes are not graded.

- **False positives: 0.**
- **Design question (1):** 999-r1 run 1 F2. Names accepted with zero length or no trailing
  NUL (`reader.rs:85-93`, same on main). The trace is right, but the behaviour matches boxcars
  0.11.5's `decode_str` exactly, and boxcars parity is the documented P1 contract
  (`replay-parser-scope.md:83, :97`). The report's supporting evidence was wrong: it quoted a
  doc line about the version floor and cited a boxcars `ZeroSize` error that does not exist.
  Grading it `false_positive` instead would put precision at 0.98.
- **Judgement calls:**
  - 666-r1 run 1 F1 bundles the non-key eviction bug with an executed second trigger that
    matches K2's `caught_if`, so it is matched to K2 with the other bug in a comment. Grading it
    `real` would put K2 at 0.00 and the case at 0.16 (one hit fewer out of 25), and overall
    recall at 0.52.
  - 999-r1 run 2 F2 ("fail closed" docs false) restates the P0 and is graded a K1 partial.
  - 999-r1 run 3 cites wrong line numbers (`header.rs:387-440`; the real lines are 121-184) for
    the right defect, so it is still caught.
  - 973-r1: spin mentioned only inside K1's explanation or fix earns no K2 credit. Counting
    those as partial would raise the case to as much as 0.65.
