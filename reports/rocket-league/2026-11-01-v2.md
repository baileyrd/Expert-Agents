## Real bugs beyond the keys

Confirmed by the graders at each case head (executed unless marked traced) and re-checked on
rusty_mill `main` at `8f27bb992`. **Not filed.** Already filed and found again: #1309 (666-r1
runs 1, 2, 4, 5 and run 5's doc claim), #1311 (1048-r1 runs 3, 5), #1312 (1048-r1 runs 1, 5,
with new evidence: on cars the ball's thresholds hide a wob_0_500 car regression — reverting cars
to the old 20/0.5/0.5 thresholds drops its error from 7.19/33.39 to 4.15/27.79, absorbed by a
raised bound), #1313 (1048-r1: the rest_40 cause, quoted residuals, cap-order comments, parity
row). No v2 run raised #1310 as a blocking finding.

New, still on main:

- **rest_* golden bounds are measured at a lag the captures don't have** (P2; 1048-r1 run 3).
  The harness's fast-start lag rule (`scenario.rs:593-601`) reads only the parked car's
  velocity, so it picks lag 3/3/1/3 for rest_10/20/40/80 (3/2/1/3 on main), while every rest
  fixture shows the ball moving on frame 1 (true lag 0). At lag 0 rest_80 exceeds its bound: head
  ball mean 3.93 against 3.6; main 2.78/8.19 against (2.7, 8.0).
- **The docs say every rl_replay error names the byte offset; three error kinds carry none**
  (P2; 999-r1 runs 2, 3). `TrailingHeaderData`, `Crc` and `UnsupportedVersion` come back from
  `rl_replay::parse` without an offset (`error.rs:1-2`, `lib.rs:10-11` and the fragment claim it).
- **rl_replay's new rejection checks are untested** (P2; 999-r1 runs 3, 4). With the array-length
  cap, the header CRC check and the `InvalidUtf8` check all disabled in a copy, every unit and
  integration test still passes. Main adds only `tests/nesting.rs`.
- **Bytes after the content section are accepted** (P2; 999-r1 run 5). Garbage appended to a valid
  replay still parses `Ok` (`lib.rs:55-63`). Graded real, not a parity design question, because
  this PR already rejects trailing header bytes that boxcars accepts.

Fixed on main since the head (`fixed_since`, 4, all 973-r1): the change fragment saying the
rolling threshold was never measured (runs 1, 4, 5; `f7f3a591c`), and the probe described as
"rolling at 600 uu/s" while it starts spinless and slides (run 3, new; executed: rolls only from
about 418 uu/s at tick 120; main's probes start rolling with an explicit `angular_velocity`).

## Grading

Graded blind against the clone at each case head by four grader agents, one per case, told to
apply v1's conventions and to probe every non-key finding (`cargo test -p`, `rb-verify` with
`RB_FORCE_ALIGN`, crafted bytes through `rl_replay::parse`, socket probes against the bridge).

- **False positives (3, 999-r1):** runs 2 and 4 call the scope doc's encoding-risk bullet
  (`replay-parser-scope.md:121-122`) false, but the vector/quaternion encodings it covers are
  gated at net_version ≥ 7 in boxcars 0.11.5 and every supported version has net ≥ 8; the gates
  they cite are different encodings. Run 4 says the `MIN_VERSION` comment misstates boxcars'
  gates; the comment is accurate about the floor and says nothing about gates above it.
- **Design questions (3):** 999-r1 run 4's names without a NUL terminator and `BoolProperty`
  accepting any byte (both match boxcars exactly; v1's parity rule); 1048-r1 run 3's slow car
  that cannot wake a sleeping ball (executed: real, but FR-037's Non-goals document it).
- **Judgement calls:** 666-r1 run 2 F3 graded a K2 partial (the eviction-before-check ordering,
  with a still-silent game rather than one holding a valid frame; executed, fixed on main by
  `2cc049473`); as non-key it would be `fixed_since` and K2 0.20. 973-r1 run 2 F2 (a doc claim
  restating K1) graded a K1 partial, following v1's 999-r1 convention. 1048-r1 runs 2 and 3 each
  have two K1 matches (dwell, joint); recall takes the best per run. 999-r1 coverage-only
  findings graded real (no v1 precedent); left ungraded, precision would be about 0.77 on that

## Harness artifact: two lost reviews

1048-r1 run 4 and 666-r1 run 3 each ended with a background-task notice arriving after the
review. The model's one-paragraph reply to it became the stored `final_text`, so the review
itself is lost: the 1048-r1 run 4 epilogue refers to "the four P2 findings above". Eval-Kit
keeps only the final turn's text, so nothing can be recovered. Both are scored as runs with
no findings, which lowers 1048-r1 and 666-r1 recall. Their duration and tokens are those of
the last turn only. The same check on the MediBoard, remind-me, agent-cloud and v1
rocket-league stores found no other such run. It needs a fix in Eval-Kit, for example keeping
the longest assistant text or failing a run whose final text is a reply to a task notice.

## Blindness, network and isolation

- **Smoke test (passed)**, with the suite's settings rendered into a scratch
  `.claude/settings.json`. `cat $EXPERT_AGENTS/README.md` returned "No such file or directory";
  `ls $TARGET` and `ls ~/.claude` printed nothing; `curl https://github.com` was refused
  (`deny network-outbound github.com:443`); `index.crates.io/config.json` answered 200.
- **Reachable domains:** `index.crates.io` and `static.crates.io`. No run's tool calls asked
  for more (no `allowed_domains` requests) or fetched the review.
- **Not isolated from other runs.** Eval-Kit `0d594ab` creates each run's `evalkit-*` project
  under the host temp root and passes `TMPDIR` through, so all 20 runs shared one `$TMPDIR`
  (`~/bench-tmp/rlv2`), which the suite does not deny; `--jobs` siblings and the concurrent
  rusty-tokio bench could read each other's scratch. A per-run private `TMPDIR` plus a deny on
  the shared temp root would close it.
- **Trace check (tool calls only):** no run named another run's `evalkit-*` directory or another
  job's scratch. Runs reused fixed names under `$TMPDIR` across cases: cargo target dirs
  (`target`, `tgt`), logs, and source trees (`scratch`, `probe`, `head`, `base`, `wt`).
  - 666-r1 runs 2 and 4 extracted the 666 head into `$TMPDIR/scratch` without clearing it.
    1048-r1 run 3 had left the 1048 head there, and that tree contains 666's key fix
    `2cc049473`.
  - That fix only modifies files that exist at the 666 head, so the overlay overwrote them. The
    only bridge-crate leftovers are two unrelated tests (`demo_count_cli.rs`,
    `probe_privacy_cli.rs`), and neither run read them.
  - The other trees that contain a key fix (1048 head: fixes for 666, 973 and 999; 973 and 999
    heads: 666's) were not under a name that a run of the affected case reused without
    `rm -rf`.
- **Shared cargo target dirs** could also have handed a run another case's stale build of a
  path dependency. A grader hit exactly that with two copies sharing one target dir, and only
  a touched source forced the rebuild. The traces hold no tool output, so whether any reviewer
  run tested a stale build cannot be checked.
