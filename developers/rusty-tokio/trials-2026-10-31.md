# rusty-tokio developer trials, 2026-10-31

Four rusty_mill issues filed from the reviewer baseline were fixed by the developer prompt,
each checked by the rusty-tokio-expert reviewer until it returned no blocking findings. All
started from base 808d6ebd9. Runs were Claude subagents in a cloud session, author-run and
not independently reproduced.

| Issue | PR | Review rounds | What the reviewer caught |
|---|---|---|---|
| #1304 watch `wait_for` predicate deadlock (P1) | #1308, approved, in merge queue | 1 + Codex | docs listed only some lock-taking calls that still deadlock (P2) |

| #1303 `Notify` drop parity | #1320 | 3 | a coop-yielded poll undid `enable()`'s consumed wakeup (P2); the re-poll change had no test (P2) |

Every first draft had its regression test red on the base and green on head. Every review
finding was real; none was a false positive. Each was a P2 the developer's own self-review
missed, so the reviewer loop is the part that earns its cost.

## Prompt changes from the trials

- Use a branch or worktree when one is given.
- Give each worktree its own `CARGO_TARGET_DIR`. A shared one let sibling worktrees overwrite each other's artifacts, and one red result came from the wrong branch.
- Tests:
  - Poll against a deadline for OS state.
  - Isolate tests that can abort (re-run the test binary as a child process).
  - Keep fallback tests in their own binary.
  - Run arithmetic bugs red in both debug and `--release`.
  - Keep a test that is green on the base only as a mutation-checked guard.
- Break your own change:
  - Poll with a spent coop budget.
  - Test every behaviour change, side effects of the fix included.
  - Show each race test red on the forbidden pattern, in both builds.
  - Check every claim in docs, fragment and commit message.
- Checks: add `cargo doc` and `cargo fmt --all`, and report how a failure in an unrelated test was handled.
- Fragment counts say which file each test is in, and are recounted after each review round.
- tokio parity tests may enable features on the tokio dev-dependency.
- Where an invariant forbids tokio's own behaviour (it panics after changing state), the invariant wins and the difference is documented.

## Found along the way, not filed

- `rusty_tokio` timer driver: `shutdown()` sets its flag and notifies without holding
  `inner`, so `event_loop` can miss it and `Runtime::drop` waits out the nearest deadline.
  Seen as a 19-minute hang of `timeout_at_with_an_already_passed_deadline_resolves_elapsed_immediately`.
  This is a source-traced cause with a gdb backtrace; the test passed on 3 reruns.
- `Notify::fire` wakes while holding the waiter's own waker mutex. `Notify` banks one permit per early `notify_one`, where tokio keeps at most one.
- `watch::Sender::send` drops the old value under the lock.
- `Semaphore::const_new` does not check `MAX_PERMITS`, unlike tokio (owner question).
- `tcp_connect_refused` is flaky under io-uring, because of an ephemeral-port race.
